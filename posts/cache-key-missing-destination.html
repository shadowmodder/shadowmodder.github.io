Your Cache Key Is Missing the Destination

Sudhir Vissa  ·  November 2026  ·  5 min read

There is a class of cache bug that never shows up in your tests, because your tests only ever talk to one backend.

The principle is simple: a cache key must capture the full identity of the request. Model, messages, parameters — and where the request is going. Miss any of those and the cache starts answering questions nobody asked it.

I ran into this in LiteLLM's response cache. Cache.get_cache_key() builds its key from the model name, the messages, and the litellm-owned kwargs — but never includes api_base. Two calls that differ only in destination produce byte-identical keys:

litellm.cache = Cache(type="local")
r1 = litellm.completion(model="gpt-4o", messages=[{"role": "user", "content": "hi"}],
                        api_base="https://backend-a.example/v1",
                        mock_response="answer from A")
r2 = litellm.completion(model="gpt-4o", messages=[{"role": "user", "content": "hi"}],
                        api_base="https://backend-b.example/v1",
                        mock_response="answer from B")
r2.content  # "answer from A" — poisoned

The second call never touches backend B. It gets backend A's cached response. In production that means one tenant's data served to another, or a staging model answering production traffic — silently, with a 200 and full confidence.

Where the dimension got lost

The root cause was in _get_model_param_value in litellm/caching/caching.py: the model component of the key only considered the model name, the model group, and the caching group. api_base is a litellm-owned kwarg, so it was excluded from the generic kwarg loop and never added explicitly. The docs even claim exact-match caches "key on a hash of the whole request" — but the destination wasn't considered part of the request.

The fix is small and surgical: in the direct-call path (no caching group, no model group), append the api_base to the key material when it's set. Router and proxy flows are untouched by construction — they always inject model_group into the metadata, so cross-deployment sharing for one model group keeps working exactly as before. Requests without api_base produce byte-identical keys to before, so it's a one-time invalidation only for the requests that were broken.

The audit

The takeaway for anyone building on LLM gateways: enumerate your cache key dimensions explicitly and write a test that varies each one. The dimensions people forget are always the environmental ones — endpoint, region, API version, tenant. Your unit tests hit one backend, so this class of bug is invisible until production. A cache that answers confidently and wrong is worse than no cache at all.

There's a useful audit for this: for every parameter your serving layer accepts, ask whether two requests differing only in that parameter should ever share a cached response. If the answer is no, it belongs in the key. Do this once per cache, in a table, and review it whenever a new parameter is added. The litellm case is what happens when the table was never written down — api_base was added as a feature, the key was designed earlier, and nobody re-checked the invariant.
