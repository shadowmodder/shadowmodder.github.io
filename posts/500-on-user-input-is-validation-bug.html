A 500 on User Input Is Always a Validation Bug

Sudhir Vissa  ·  November 2026  ·  5 min read

Here's a rule I hold myself to: if user input can produce a 500, the bug is in validation, not in the code that crashed. The crash is just where the missing check became visible.

vLLM's Responses API had a clean instance. Sending an assistant message with an empty content list — {"type": "message", "role": "assistant", "content": []} — in the input array of a /v1/responses request passed request validation without complaint. The item got coerced into a ResponseOutputMessage with content=[], traveled through the serving layer, and then died in rendering:

IndexError: list index out of range
  at _construct_message_from_response_item (item.content[0].text)

The client got a 500. Nothing about their request was unreasonable enough to deserve one — an empty list is a degenerate but well-formed input, and the API's own types (ResponseOutputMessage allows content=[]) accepted it.

Two layers, two contracts

The root cause sat in input_item_parsing in vllm/entrypoints/openai/responses/protocol.py: when coercing assistant messages with list content, it added the id, status, and annotations but never checked whether the content list was empty. Validation said yes; the renderer assumed non-empty. Two layers, two different contracts, and the gap between them was a 500.

The fix follows the precedent the vLLM team itself set in #55974 — "reject with 400 instead of 500." In input_item_parsing, raise VLLMValidationError("Assistant message content must not be empty.", parameter="input") when an assistant message arrives with an empty content list. One check, at the boundary, before the object ever enters the system. A regression test asserts the 400 and that non-empty messages still validate fine.

↗ vllm-project/vllm#64941

Validate the invariants, not just the shapes

The general lesson: validate at the boundary, and validate the invariants your downstream code assumes, not just the shapes your schema declares. Pydantic will happily tell you content is a list. It won't tell you the renderer needs that list to be non-empty. Every content[0] in your codebase is a validation obligation somewhere upstream — go find the ones that don't have it.

And when you fix one, check the siblings: empty reasoning items, None content, missing text fields. In this case the neighbors were all handled. The one that wasn't is always the one nobody wrote down.

There's a process version of this too. The vLLM team had already decided the policy in #55974 — bad input gets a 400, not a 500. Precedents like that are only useful if new code is checked against them. When your team establishes a "this class of input is rejected at the boundary" rule, the follow-through is grepping for the next instance, not just fixing the reported one. The bug I found was the second occurrence of a decided question.

For the record

I found this bug and filed the fix — #64941, then a revised version, #66475. By the time my PRs were sitting in vLLM's review queue, the same ground had already been covered upstream: #35508 by anencore94, which normalizes Responses input items to match the OpenAI SDK's requirements, had landed the correct behavior on main. When a test against current main showed the 400 already coming back, I closed both of my PRs. Credit where it's due — the fix in the tree is theirs.

I'm publishing the analysis anyway. The find was real even though the merge isn't mine, and the validation gap is the part worth remembering. Spotting a bug first is worth little; what counts is whose fix ships.
